# TraceFlow — анализ графа денежных переводов

TraceFlow — прототип для изучения сети переводов и выбора клиентов, которых аналитику стоит проверить в первую очередь. Проект подготовлен для кейса HackAlem AI «Граф денег».

## Какую задачу решает

В больших наборах переводов сложно вручную увидеть, кто собирает деньги от нескольких отправителей, передаёт их дальше или связывает разные ветви сети. TraceFlow строит ориентированный граф переводов, рассчитывает показатели узлов и показывает аналитические результаты в интерфейсе Streamlit.

Инструмент предназначен для аналитика, который исследует предоставленную транзакционную выгрузку. Роли и приоритет — объяснимые эвристические подсказки для проверки, а не доказательство нарушения или вины.

## Что реализовано

- Загрузка `nodes.parquet`, `edges.parquet` и `transactions.parquet` из локальной папки с данными.
- Построение ориентированного графа NetworkX со всеми узлами из таблицы узлов, включая изолированные.
- Расчёт метрик узлов: глубина, seed-флаг, входящие и исходящие степени, суммы и число переводов, уникальные отправители и получатели, `pass_through`, PageRank, betweenness и признак обрезания графа на глубине 4.
- Назначение одной из эвристических ролей: `consolidator`, `transit`, `distributor`, `terminal`, `coordinator` или `peripheral`. Для каждой роли экспортируются оценка и текстовое обоснование (`evidence`).
- Расчёт приоритета проверки по шкале **0–100** на основе объёма, числа контрагентов, дисбаланса входящих и исходящих сумм и seed-флага.
- Кластеризация переводной сети: локальная детерминированная реализация Louvain-подобного поиска сообществ по модулярности.
- Формирование `output/node_metrics.csv`, `output/nodes_roles.csv`, `output/clusters.csv` и `output/top_nodes.csv`.
- Интерфейс Streamlit: карточка клиента, поиск по GID, просмотр входящих и исходящих связей, переход к контрагенту, таблица Top Nodes, каталог клиентов и кластеров, дневная сводка транзакций и скачивание результатов.
- Отдельный mock-режим с синтетическими CSV для демонстрации интерфейса без выдачи примера за анализ реальных данных.

## Как работает решение

1. Pipeline читает узлы, агрегированные рёбра и транзакции из Parquet.
2. Из узлов и агрегированных рёбер собирается ориентированный граф; для каждого GID рассчитываются метрики.
3. На основе метрик применяются правила ролей и приоритета, а рёбра используются для выделения кластеров.
4. Pipeline сохраняет метрики и три CSV с ролями, кластерами и ранжированным списком для проверки.
5. Streamlit читает готовые CSV и исходные связи, позволяет найти GID и изучить его окружение. Интерфейс отображает аналитические оценки, а не пересчитывает их.

## Технологии

| Область | Используется |
| --- | --- |
| Язык | Python |
| Анализ таблиц и Parquet | pandas, NumPy, PyArrow |
| Граф и сетевые метрики | NetworkX, SciPy |
| Веб-интерфейс | Streamlit |
| Проверки | `unittest`, Streamlit AppTest |
| Внешние API, облачные сервисы | В текущем репозитории не используются |
| AI/ML-модель | Не подключена; роли, оценки и кластеры формируются кодом проекта |

Граф связей для интерфейса рисуется кодом приложения; отдельный внешний графический сервис не требуется.

## Архитектура проекта

```text
data (1)/data/*.parquet
          │
          ▼
src/loader.py ──► src/graph_builder.py ──► src/metrics.py
                                              │
                                              ▼
                                  output/node_metrics.csv
                                              │
                          src/roles.py + src/priority.py
                          + src/clustering.py + src/export.py
                                              │
                    ┌─────────────────────────┼─────────────────────┐
                    ▼                         ▼                     ▼
          output/nodes_roles.csv   output/clusters.csv   output/top_nodes.csv
                    └─────────────────────────┬───────────────────┘
                                              ▼
                                      Streamlit: ui/app.py
```

Основные компоненты:

- `src/loader.py` — чтение трёх исходных Parquet-файлов.
- `src/graph_builder.py` — построение `networkx.DiGraph` и добавление узлов.
- `src/metrics.py` — расчёт и сохранение метрик узлов.
- `src/roles.py`, `src/priority.py` — эвристические роли, оценки и обоснования.
- `src/clustering.py` — детерминированная локальная оптимизация модулярности для кластеров.
- `src/export.py` — запись CSV-результатов.
- `ui/app.py` и модули в `ui/` — чтение CSV и исходных данных, поиск клиента, карточка, граф связей, каталог и выгрузки.
- `mock/` — синтетические CSV для демонстрационного режима.
- `tests/` — проверки аналитики, интеграции и поведения UI.

## Установка и запуск

Рекомендуется Python 3.12. Команды ниже приведены для PowerShell из корневой папки репозитория.

### 1. Создать виртуальное окружение и установить зависимости

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements-ui.txt
python -m pip install networkx numpy scipy
```

`requirements-ui.txt` содержит зависимости интерфейса и чтения Parquet. Для аналитического pipeline дополнительно устанавливаются NetworkX, NumPy и SciPy.

### 2. Запустить аналитику

Исходные файлы по умолчанию находятся в `data (1)/data/`. Pipeline создаст папку `output/` при необходимости:

```powershell
python src/pipeline.py --data "data (1)/data" --output-dir output
```

Основные параметры:

- `--data` — путь к папке с `nodes.parquet`, `edges.parquet` и `transactions.parquet`;
- `--output-dir` — каталог для CSV; по умолчанию `output` в корне проекта.

### 3. Запустить интерфейс

```powershell
python -m streamlit run ui/app.py
```

Откройте адрес, напечатанный Streamlit (обычно `http://localhost:8501`). В боковой панели доступны автоматический выбор готовых результатов или mock, отдельный mock-режим и просмотр исходных данных.

Чтобы указать другие каталоги до запуска приложения, задайте переменные окружения:

```powershell
$env:TRACEFLOW_RESULTS_DIR = "C:\path\to\results"
$env:TRACEFLOW_DATA_DIR = "C:\path\to\data"
python -m streamlit run ui/app.py
```

## Как проверить решение

### Повторяемый сценарий для жюри

1. Установите зависимости и запустите pipeline командами выше.
2. Запустите Streamlit и откройте локальную страницу.
3. В режиме исходных данных введите GID из выгрузки в поиск и откройте карточку. Проверьте роль, приоритет, обоснование и направления связей.
4. Откройте Top Nodes и каталог, затем проверьте CSV в `output/`.
5. Чтобы увидеть интерфейс без pipeline и исходной аналитики, переключитесь на демонстрационный mock-режим и найдите GID `901245`. Это синтетический пример.

Для проверки пограничного случая на глубине 4 можно искать GID `100000000404740100`, а для изолированного клиента — `100000000456947100`, если эти записи присутствуют в приложенной выгрузке. Отсутствие исходящих связей на глубине 4 не следует трактовать как подтверждение остановки денежного потока.

### Запустить тесты

```powershell
python -m unittest discover -s tests -v
```

Тесты находятся в `tests/` и покрывают аналитику, интеграционные сценарии и UI.

## Данные и интеграции

Источники — локальные файлы проекта:

| Файл | Роль в решении |
| --- | --- |
| `nodes.parquet` | GID, глубина обхода и признак seed; также сохраняются узлы без наблюдаемых рёбер |
| `edges.parquet` | Агрегированные направленные связи, сумма и число переводов; основа графа и метрик |
| `transactions.parquet` | Отдельные записи переводов с датой; используются, в частности, для дневной сводки клиента в UI |

По умолчанию исходные данные ищутся в `data (1)/data/`, а результаты pipeline пишутся в `output/`. Директории можно переопределить указанными выше аргументами и переменными окружения.

Приложение не отправляет данные в сторонние API и не требует облачного аккаунта. Для работы используются локальные файлы и установленные Python-библиотеки.

## Ограничения текущей версии

- Выгрузка ограничена глубиной 4. Отсутствие исходящих рёбер у узла на границе — ограничение наблюдения, а не доказательство того, что средства остановились.
- У seed-узлов входящая история может быть неполной, поэтому рассчитанный по доступной выгрузке `pass_through` не описывает полный денежный поток.
- Роли и приоритет основаны на эвристических правилах; эталонной разметки для проверки качества ролей в проекте нет. Результаты требуют проверки аналитиком.
- `priority_score` формируется в диапазоне 0–100. Это шкала приоритета проекта, а не вероятность и не оценка виновности.
- Реализация кластеризации в `src/clustering.py` выполняет локальные перемещения для оптимизации модулярности; она не использует отдельную библиотеку Louvain.
- UI загружает таблицы целиком и рассчитан на размер текущей выгрузки. Для существенно более крупной сети понадобятся серверная фильтрация, пагинация и индексы.
- Интерфейс доступен локально. Файла конфигурации или подтверждённой ссылки на опубликованную версию в репозитории нет.
