# TraceFlow — анализ графа денежных переводов

TraceFlow — прототип для изучения сети переводов и выбора клиентов, которых аналитику стоит проверить в первую очередь. Проект подготовлен для кейса HackAlem AI «Граф денег».

## Объединённая версия в `main`

В `main` собраны все три части решения. Для полного запуска достаточно этой ветки:

| Исходная ветка | Что вошло в общее решение |
| --- | --- |
| `dev/data-metrics` | Проверка Parquet, ориентированный граф, метрики всех GID и сохранение изолированных узлов |
| `analytics` | Правила шести ролей, приоритет 0–1, объяснения до 200 символов, кластеры и CSV-отчёты |
| `dev/ui` | Поиск GID, направленные связи, навигация между клиентами, Top Nodes и сводка для скачивания |

Исходные Parquet находятся в **`data/`**. Результаты создаются локально в **`output/`** и исключены из Git. После первого клонирования запустите pipeline, чтобы интерфейс показал анализ приложенной выгрузки. Без аналитических CSV автоматический режим открывает явно обозначенный синтетический пример.

## Какую задачу решает

В больших наборах переводов сложно вручную увидеть, кто собирает деньги от нескольких отправителей, передаёт их дальше или связывает разные ветви сети. TraceFlow строит ориентированный граф переводов, рассчитывает показатели узлов и показывает аналитические результаты в интерфейсе Streamlit.

Инструмент предназначен для аналитика, который исследует предоставленную транзакционную выгрузку. Роли и приоритет — объяснимые эвристические подсказки для проверки, а не доказательство нарушения или вины.

## Что реализовано

- Загрузка и проверка `nodes.parquet`, `edges.parquet` и `transactions.parquet`: схемы, уникальность и точность GID, положительные суммы, соответствие направленных рёбер агрегатам транзакций.
- Построение ориентированного графа NetworkX со всеми узлами из таблицы узлов, включая изолированные.
- Расчёт метрик узлов: глубина, seed-флаг, входящие и исходящие степени, суммы и число переводов, уникальные отправители и получатели, `pass_through`, PageRank, betweenness и признак обрезания графа на глубине 4.
- Назначение одной из эвристических ролей: `consolidator`, `transit`, `distributor`, `terminal`, `coordinator` или `peripheral`. Для каждой роли экспортируются оценка и текстовое обоснование (`evidence`).
- Расчёт приоритета проверки по шкале **0–1** на основе объёма, числа контрагентов, дисбаланса входящих и исходящих сумм и seed-флага. Приоритет сохраняется с тремя знаками после запятой, `evidence` ограничен 200 символами.
- Кластеризация переводной сети: локальная детерминированная реализация Louvain-подобного поиска сообществ по модулярности.
- Полный запуск из Parquet формирует пять файлов: `output/node_metrics.csv`, `output/edges.csv`, `output/nodes_roles.csv`, `output/clusters.csv` и `output/top_nodes.csv`.
- Интерфейс Streamlit: карточка клиента, поиск по GID, фильтр входящих и исходящих связей, переход к контрагенту и возврат, таблица Top Nodes, каталог клиентов и кластеров, дневная сводка транзакций и скачивание результатов. Для выбранного GID можно сохранить Markdown-сводку с объяснениями, связями и ограничениями наблюдения.
- Счётчики Dashboard: число клиентов и связей, количество транзакций по `n_tx`, сумма переводов по `sum_kzt` и размер очереди проверки.
- Отдельный mock-режим с синтетическими CSV для демонстрации интерфейса без выдачи примера за анализ реальных данных.

## Как работает решение

1. Pipeline читает узлы, агрегированные рёбра и транзакции из Parquet.
2. Из узлов и агрегированных рёбер собирается ориентированный граф; для каждого GID рассчитываются метрики.
3. На основе метрик применяются правила ролей и приоритета, а рёбра используются для выделения кластеров.
4. Pipeline сохраняет метрики, исходные направленные рёбра и три CSV с ролями, кластерами и ранжированным списком для проверки.
5. Streamlit читает готовые CSV и исходные связи, позволяет найти GID и изучить его окружение. Интерфейс отображает аналитические оценки, а не пересчитывает их.

## Технологии

| Область | Используется |
| --- | --- |
| Язык | Python |
| Анализ таблиц и Parquet | pandas, NumPy, PyArrow |
| Граф и сетевые метрики | NetworkX, SciPy |
| Веб-интерфейс | Streamlit |
| Проверки | `unittest`, Streamlit AppTest |
| Внешние API, облачные сервисы | В текущем репозитории не используются |
| AI/ML-модель | Не подключена; роли, оценки и кластеры формируются кодом проекта |

Граф связей для интерфейса рисуется кодом приложения; отдельный внешний графический сервис не требуется.

## Архитектура проекта

```mermaid
flowchart TD
    A["data/: nodes, edges, transactions.parquet"] --> B["loader: проверка таблиц и агрегатов"]
    B --> C["DiGraph и метрики узлов"]
    C --> D["node_metrics.csv"]
    B --> E["edges.csv: исходные направленные связи"]
    D --> F["roles + priority"]
    D --> G["clustering"]
    E --> G
    F --> H["export: nodes_roles, clusters, top_nodes.csv"]
    G --> H
    H --> I["Streamlit: поиск и проверка GID"]
    D --> I
    E --> I
    A -. "даты отдельных транзакций" .-> I
```

Основные компоненты:

- `src/loader.py` — чтение и проверка трёх исходных Parquet-файлов.
- `src/pipeline.py` — единая точка запуска полного расчёта из Parquet или аналитического этапа из готовых CSV.
- `src/graph_builder.py` — построение `networkx.DiGraph` и добавление узлов.
- `src/metrics.py` — расчёт и сохранение метрик узлов.
- `src/roles.py`, `src/priority.py` — эвристические роли, оценки и обоснования.
- `src/clustering.py` — детерминированная локальная оптимизация модулярности для кластеров.
- `src/export.py` — запись CSV-результатов.
- `ui/app.py` и модули в `ui/` — чтение CSV и исходных данных, поиск клиента, карточка, граф связей, каталог и выгрузки.
- `mock/` — синтетические CSV для демонстрационного режима.
- `tests/` — проверки аналитики, интеграции и поведения UI.

Для кластеризации строится взвешенная неориентированная проекция рёбер. UI показывает исходное направление переводов из `edges.csv`. Подробности: [контракты и передача результатов](docs/integration.md), [правила аналитики](analytics.md).

## Установка и запуск

Используйте Python 3.12.10. Команды ниже приведены для PowerShell из корневой папки репозитория. Команда `py -3.12 --version` должна показать установленную версию; при необходимости сначала установите Python 3.12.10.

### 1. Получить проект

```powershell
git clone https://github.com/BAITC-Hacks/hack-c4e364b4-shakarim.git
cd hack-c4e364b4-shakarim
git switch main
```

Если проект уже скачан, откройте его корневую папку — ту, где находятся `src/`, `ui/` и `requirements-test.txt` — и обновите чистую рабочую копию:

```powershell
git switch main
git pull --ff-only origin main
```

### 2. Создать виртуальное окружение и установить зависимости

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe --version
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements-test.txt
```

`requirements-test.txt` включает зависимости полного pipeline, интерфейса и тестов. Для автономной демонстрации только UI достаточно `requirements-ui.txt`. Создавайте `.venv` на своей машине: готовое окружение из другой папки или с другого компьютера может содержать неверный путь к Python.

Команды используют интерпретатор `.venv` напрямую, поэтому активация окружения в PowerShell не требуется.

### 3. Запустить аналитику

Исходные файлы находятся в `data/`. Pipeline создаст папку `output/` при необходимости:

```powershell
.\.venv\Scripts\python.exe src/pipeline.py --data data --output-dir output
```

Основные параметры:

- `--data` — путь к папке с `nodes.parquet`, `edges.parquet` и `transactions.parquet`;
- `--input` — готовый CSV с одной строкой метрик на GID для запуска аналитического этапа;
- `--edges` — CSV направленных рёбер для кластеризации при запуске с `--input`;
- `--output-dir` — каталог для CSV; по умолчанию `output` в корне проекта.

Чтобы повторно рассчитать роли, приоритеты и кластеры по готовым метрикам:

```powershell
.\.venv\Scripts\python.exe src/pipeline.py --input output/node_metrics.csv --edges output/edges.csv --output-dir output
```

При запуске с `--input` без `--edges` каждый узел получает отдельный кластер: связи нельзя восстановить из агрегированных метрик. Для полноценного анализа используйте рёбра того же набора данных.

Режим `--input` обновляет только три аналитических отчёта. Если указан новый `--output-dir`, скопируйте туда `node_metrics.csv` и `edges.csv` того же набора данных для передачи полного комплекта в UI. Аргументы `--data` и `--input` взаимно исключаются; `--edges` предназначен для анализа CSV.

### 4. Запустить интерфейс

```powershell
.\.venv\Scripts\python.exe -m streamlit run ui/app.py
```

Откройте адрес, напечатанный Streamlit (обычно `http://localhost:8501`). В боковой панели доступны автоматический выбор готовых результатов или mock, отдельный mock-режим и просмотр исходных данных. После расчёта нажмите «Обновить данные». В режиме «Авто» mock открывается только при полном отсутствии аналитических CSV; частичная или повреждённая выгрузка показывает проблему загрузки.

Чтобы указать другие каталоги до запуска приложения, задайте переменные окружения:

```powershell
$env:TRACEFLOW_RESULTS_DIR = "C:\path\to\results"
$env:TRACEFLOW_DATA_DIR = "C:\path\to\data"
.\.venv\Scripts\python.exe -m streamlit run ui/app.py
```

После обновления кода остановите ранее запущенный Streamlit через `Ctrl+C` и запустите его снова. Для обновления только CSV достаточно кнопки «Обновить данные».

## Работа с интерфейсом

| Вкладка | Что доступно |
| --- | --- |
| **Dashboard** | Карточка выбранного GID, роль, приоритет, кластер, объяснения, граф связей, первые пять узлов очереди и скачивание сводки |
| **Top Nodes** | Таблица первых 20 узлов; переход к любому GID из загруженной очереди |
| **Клиенты и кластеры** | Каталог клиентов с фильтрами и таблица кластеров |
| **Выгрузки и ограничения** | Скачивание трёх аналитических CSV в режиме результатов и описание границ наблюдения |

Pipeline экспортирует до 100 узлов в `top_nodes.csv`; поэтому количество строк в файле может превышать число строк, показанных в таблице Top Nodes.

Режим выбирается в боковой панели:

- **Авто: output → mock** — загружает готовую аналитику. Mock используется только при отсутствии всех трёх аналитических CSV. Частичная или некорректная выгрузка вызывает сообщение о проблеме.
- **Демо: mock CSV** — синтетический пример для проверки интерфейса; поиск `901245` открывает демонстрационный профиль.
- **Исходные данные** — показывает наблюдаемые переводы без рассчитанных ролей, приоритетов, кластеров и очереди проверки.

В mock-режиме и режиме исходных данных скачивание трёх аналитических отчётов отключено. Направления связей, поиск и доступные наблюдения можно изучать в соответствующем режиме.

## Как проверить решение

### Повторяемый сценарий для жюри

1. Установите зависимости и запустите pipeline командами выше.
2. Запустите Streamlit и откройте локальную страницу.
3. Выберите «Авто: output → mock», убедитесь, что источник — готовые результаты pipeline. Введите GID из выгрузки, например `100000003016635100`, и откройте профиль. Проверьте роль, приоритет, обоснование и направления связей. Режим «Исходные данные» показывает переводы без рассчитанных ролей и оценок.
4. Откройте Top Nodes, перейдите к клиенту и затем к его контрагенту. Проверьте возврат и «Скачать сводку по GID», откройте пять CSV в `output/`.
5. Чтобы увидеть интерфейс без pipeline и исходной аналитики, переключитесь на демонстрационный mock-режим и найдите GID `901245`. Это синтетический пример.

Для проверки пограничного случая на глубине 4 можно искать GID `100000000404740100`, а для изолированного клиента — `100000000456947100`, если эти записи присутствуют в приложенной выгрузке. Отсутствие исходящих связей на глубине 4 не следует трактовать как подтверждение остановки денежного потока.

Для приложенного датасета интеграционные проверки ожидают 2 248 узлов, 3 119 направленных рёбер и 4 840 транзакций, включая 19 изолированных seed-узлов. Подробный сценарий защиты и примеры GID находятся в [docs/demo.md](docs/demo.md).

## Данные и интеграции

Источники — локальные файлы проекта:

| Файл в `data/` | Обязательные колонки | Роль в решении |
| --- | --- | --- |
| `nodes.parquet` | `gid, depth, is_seed` | Все клиенты, включая узлы без наблюдаемых рёбер |
| `edges.parquet` | `src, dst, sum_kzt, n_tx, depth` | Агрегированные направленные связи для графа и метрик |
| `transactions.parquet` | `src, dst, date, sum_kzt` | Сверка сумм и количества переводов по каждой паре; дневная история клиента |

По умолчанию исходные данные находятся в `data/`, а результаты pipeline пишутся в `output/`. Директории можно переопределить указанными выше аргументами и переменными окружения. Сгенерированные CSV исключены из Git и создаются командой запуска pipeline; синтетический `mock/` хранится в репозитории.

Файлы полного запуска в `output/`:

| Файл | Колонки |
| --- | --- |
| `node_metrics.csv` | `gid, depth, is_seed, in_degree, out_degree, in_amount, out_amount, in_tx_count, out_tx_count, unique_senders, unique_receivers, pass_through, pagerank, betweenness, truncated_by_depth` |
| `edges.csv` | `src, dst, sum_kzt, n_tx, depth` из исходной таблицы рёбер |
| `nodes_roles.csv` | `gid, role, role_score, cluster_id, priority_score, evidence` |
| `clusters.csv` | `cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis` |
| `top_nodes.csv` | `rank, gid, role, priority_score, why` |

Pipeline сохраняет GID как `int64` в таблицах исходных данных и метрик. Интерфейс читает идентификаторы как строки, чтобы браузер не округлял 18-значные значения. При переносе результатов используйте пять CSV одного запуска. Для дневной истории переводов дополнительно нужен `transactions.parquet`.

`pass_through = out_amount / in_amount`, если входящая сумма положительна; у seed он остаётся пустым. PageRank взвешен по `sum_kzt`, а betweenness использует длину ребра `1 / sum_kzt`. Признак `truncated_by_depth` установлен при `depth >= 4` и `out_degree == 0`.

Приложение не отправляет данные в сторонние API и не требует облачного аккаунта. Для работы используются локальные файлы и установленные Python-библиотеки.

## Ограничения текущей версии

- Выгрузка ограничена глубиной 4. Отсутствие исходящих рёбер у узла на границе — ограничение наблюдения, а не доказательство того, что средства остановились.
- У seed-узлов входящая история неполна; `pass_through` для них оставляется пустым (`NaN`).
- Роли и приоритет основаны на эвристических правилах; эталонной разметки для проверки качества ролей в проекте нет. Результаты требуют проверки аналитиком.
- PageRank и betweenness доступны в метриках, но текущие правила ролей и приоритета их не используют. Правила ролей заново вычисляют отношение доступных сумм; неполнота данных seed остаётся ограничением интерпретации.
- `priority_score` формируется в диапазоне 0–1. Это шкала приоритета проекта, а не вероятность и не оценка виновности.
- Реализация кластеризации в `src/clustering.py` выполняет локальные перемещения для оптимизации модулярности; она не использует отдельную библиотеку Louvain.
- UI загружает таблицы целиком и рассчитан на размер текущей выгрузки. Граф показывает до 10 соседей на странице, остальных можно открыть переключателем. Для существенно более крупной сети понадобятся серверная фильтрация и индексы.
- Pipeline требует минимум 20 узлов для формирования `top_nodes.csv`.
