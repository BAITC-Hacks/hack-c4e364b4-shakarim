# Аналитический модуль

Аналитический этап анализирует готовые метрики узлов. Для каждого `gid` он назначает роль, считает `role_score` и `priority_score`, формирует пояснение `evidence` и сохраняет три CSV-отчёта. Общий `src/pipeline.py` также умеет сначала загрузить Parquet, проверить данные и рассчитать графовые метрики.

## Запуск

Полный запуск из исходных Parquet:

```powershell
python src/pipeline.py --data data --output-dir output
```

Он сохраняет `node_metrics.csv`, `edges.csv`, три аналитических отчёта и `analysis_context.json`. Для повторного запуска аналитического этапа по готовым метрикам:

```powershell
python src/pipeline.py --input output/node_metrics.csv --output-dir output
```

Чтобы выполнить кластеризацию Louvain, передайте CSV рёбер:

```powershell
python src/pipeline.py --input output/node_metrics.csv --edges output/edges.csv --output-dir output
```

Без аргументов pipeline ищет исходную папку Parquet и запускает полный расчёт; если исходных данных нет, использует готовый `node_metrics.csv` из каталога результатов. Для воспроизводимой демонстрации указывайте `--data` или `--input` явно.

## Входные данные

`node_metrics.csv` содержит одну строку на один `gid`. Используются следующие метрики, рассчитанные до аналитического этапа:

CSV-вход требует уникальный непустой `gid`, `in_amount`, `out_amount`, `unique_senders` и `unique_receivers` (допустимы синонимы из `ALIASES` в `roles.py`, в том числе степени вместо числа уникальных соседей). Суммы должны быть конечными и неотрицательными, счётчики — целыми неотрицательными. Если глубина, seed или счётчики операций отсутствуют, используются значения по умолчанию; для полноценного учёта границ наблюдения передавайте полный контракт метрик.

| Колонка | Назначение |
| --- | --- |
| `gid` | Идентификатор узла. Обязателен и должен быть уникален. |
| `depth` | Глубина узла от seed. На глубине 4 отсутствие исходящих операций не доказывает terminal-роль. |
| `is_seed` | Признак исходного seed-узла. |
| `in_amount`, `out_amount` | Входящий и исходящий денежный объём. |
| `in_degree`, `out_degree` | Число входящих и исходящих соседей. |
| `unique_senders`, `unique_receivers` | Число уникальных контрагентов. |
| `in_tx_count`, `out_tx_count` | Число входящих и исходящих транзакций. |
| `pass_ratio`, `pass_through` | Отношение исходящего объёма к входящему; оба поля одинаковы, у seed и при нулевом входе пустые. Правила используют суммы с учётом ограничений наблюдения. |
| `pagerank`, `betweenness` | Сохранённые графовые метрики; в текущих правилах ролей напрямую не используются. |

При анализе готовых метрик `edges.csv` нужен для кластеризации; UI использует его для направленного графа связей. Общий pipeline экспортирует `src`, `dst`, `sum_kzt`, `n_tx`, `depth`. Аналитический CSV-вход также поддерживает `source`, `target`, `amount` и синонимы `source_gid`, `target_gid`, `amount_kzt`. Каждый `gid` в рёбрах должен присутствовать в `node_metrics.csv`.

## Что делает каждый файл

| Файл | Функция |
| --- | --- |
| `src/pipeline.py` | Запускает полный расчёт из Parquet или читает готовые CSV, проверяет уникальность `gid`, запускает роли, приоритеты, кластеризацию и экспорт. |
| `src/roles.py` | Присваивает одну из шести ролей, считает `role_score`, создаёт короткий `evidence`. |
| `src/priority.py` | Считает `priority_score` от 0 до 1. |
| `src/clustering.py` | Строит взвешенную неориентированную проекцию и выполняет многоуровневый Louvain средствами NetworkX. |
| `src/export.py` | Записывает отчёты в фиксированных схемах CSV. |
| `tests/test_analytics.py` | Регрессионные проверки ролей, баллов, границы `depth=4`, кластеризации, экспорта и входных ограничений. |

## Роли

Правила проверяются по порядку. Первое совпадение назначает единственную роль; `role_score` не меняет выбранную роль.

Сначала проверяется граница наблюдения: `truncated_by_depth=true` либо `depth >= 4` при отсутствии исходящей суммы, получателей, операций и степени. Такой узел получает `peripheral` с `role_score=0.2`: отсутствие наблюдаемого выхода не доказывает удержание или консолидацию денег. Затем действуют правила:

| Порядок | Роль | Обычный узел | Seed с неполным входящим потоком |
| --- | --- | --- | --- |
| 1 | `peripheral` | Нулевой оборот либо сумма числа отправителей и получателей ≤ 2 и суммарное число транзакций ≤ 2 | То же правило |
| 2 | `terminal` | Положительный вход; выход ≤ 20% входа | Не назначается |
| 3 | `coordinator` | ≥ 5 отправителей, ≥ 5 получателей; меньший денежный объём ≥ 50% большего | ≥ 5 отправителей и ≥ 5 получателей, без сравнения денежных потоков |
| 4 | `consolidator` | ≥ 3 отправителей; вход > 120% выхода | Положительный вход, ≥ 3 отправителей и отправителей ≥ `2 × max(получателей, 1)` |
| 5 | `distributor` | ≥ 3 получателей; выход > 120% входа | Положительный выход, ≥ 3 получателей и получателей ≥ `2 × max(отправителей, 1)` |
| 6 | `transit` | Положительные вход и выход; выход составляет 75–125% входа | Не назначается |
| 7 | `peripheral` | Ни одно из предыдущих правил не выполнено | То же правило |

Количество контрагентов в формулах — сумма двух направленных счётчиков: один человек, переводивший в обе стороны, может учитываться и как отправитель, и как получатель. Seed-роли являются структурными гипотезами по наблюдаемым соседям; баланс денег не используется.

### Формулы `role_score`

Обозначения: `I`, `O` — входящая и исходящая суммы KZT; `S`, `R` — числа отправителей и получателей; `Ni`, `No` — числа входящих и исходящих транзакций. `T = I + O`, `B = min(I,O) / max(I,O)` (0 при нулевом обороте), `P = O / I` (0 при нулевом входе), `C(x) = min(1,x)`.

| Роль | Формула |
| --- | --- |
| `coordinator` | `0.45 × C(ln(1+S+R)/ln(101)) + 0.35 × B + 0.20 × C(T/1_000_000)` |
| `consolidator` | `0.45 × C(S/10) + 0.35 × max(0,I-O)/max(I,1) + 0.20 × C(I/1_000_000)` |
| `distributor` | `0.45 × C(R/10) + 0.35 × max(0,O-I)/max(O,1) + 0.20 × C(O/1_000_000)` |
| `transit` | `0.60 × B + 0.15 × C(No/max(Ni,1)) + 0.25 × C(T/1_000_000)` |
| `terminal` | `0.55 × (1-C(P)) + 0.25 × C(I/500_000) + 0.20 × C(S/5)` |
| `peripheral` | `0.60` для малой/нулевой наблюдаемой активности; `0.20` для границы выгрузки или неопределённой роли |

У seed второй компонент с весом `0.35` равен нулю: обрезанный вход нельзя использовать для сравнения потоков. Итог ограничивается диапазоном `[0.05, 1]` и округляется до трёх знаков. Это эвристическая сила признаков, не калиброванная вероятность правильности роли.

`evidence` содержит конкретные суммы, число контрагентов или долю перевода и ограничено 200 символами. Для seed и границы глубины добавляется оговорка о неполноте данных. Числа от `10^12` отображаются в компактной научной записи; слишком длинное пояснение сокращается с многоточием.

## Приоритет

`priority_score` находится в диапазоне 0–1 и составляется из ограниченных компонентов:

| Компонент | Формула вклада | Максимум |
| --- | --- | --- |
| Денежный оборот | `0.45 × min(1, ln(1+I+O)/ln(1+10_000_000))` | 0.45 |
| Связность | `0.25 × min(1, ln(1+S+R)/ln(101))` | 0.25 |
| Дисбаланс потоков | `0.20 × abs(I-O)/max(I+O,1)` | 0.20 |
| Seed | `0.10`, если `is_seed=true`, иначе 0 | 0.10 |

У seed и узлов с обрезанным наблюдением на границе глубины компонент дисбаланса **равен нулю**. Неполнота входа/выхода не должна сама повышать приоритет на 0.20. Остальные компоненты по наблюдаемым данным сохраняются; пропущенный вклад не перераспределяется.

Итог — сумма компонентов, ограниченная `[0,1]` и округлённая до трёх знаков. Больший score означает более высокий приоритет ручной проверки. Логарифмические шкалы ограничивают влияние очень крупного оборота; коэффициенты эвристические и не обучены на размеченных случаях.

Поле `why` в `top_nodes.csv` содержит итоговый score, численный вклад каждого из четырёх компонентов и evidence роли. Каждый вклад отображается с тремя знаками: их округлённая сумма может отличаться от итогового округлённого score на 0.001.

## Кластеризация

При передаче `--edges` направленные связи переводятся во взвешенную неориентированную проекцию. Веса повторных рёбер и переводов в обоих направлениях суммируются. NetworkX `louvain_communities` выполняет многоуровневую оптимизацию модулярности с `weight="weight"`, `resolution=1`, `seed=42`.

Порядок вставки узлов и рёбер фиксирован. Сообщества сортируются по минимальному строковому GID и получают ID начиная с 1; изолированные узлы сохраняются в отдельных сообществах. Повторный запуск с теми же данными и версиями библиотек воспроизводим. Переводы самому себе исключены только из поиска сообществ, но сохраняются в сумме внутренних переводов кластера.

Направление не теряется из аналитики: входящие и исходящие суммы, степени и транзакционные счётчики остаются в строке `node_metrics.csv` и используются в правилах ролей и приоритета.

При запуске с `--input` без `--edges` связи нельзя восстановить из агрегированных метрик. Pipeline назначает каждому узлу отдельный `cluster_id`, а `clusters.csv` сообщает об отсутствии исходных связей. В полном запуске через `--data` используются направленные рёбра из Parquet.

## Выходные файлы

Схемы фиксированы в `src/export.py`.

До записи проверяются уникальность GID, обязательные поля, допустимые роли, конечность и диапазон обеих оценок, длина evidence, соответствие размеров кластеров и допустимость денежных сумм. Сначала все файлы готовятся во временном каталоге; после успешного расчёта и проверок заменяются итоговые файлы. Ошибка входных данных или валидации не публикует частично рассчитанный отчёт.

Оба режима публикуют пять CSV и `analysis_context.json`. В режиме `--input` поддерживаемые синонимы колонок метрик заменяются каноническими именами, а рёбра записываются с `src,dst,sum_kzt`; дополнительные переданные поля сохраняются. Значения метрик не пересчитываются. Если `--edges` не указан, создаётся пустой `edges.csv` с заголовком, чтобы UI не использовал связи от прошлого набора данных.

Контекст имеет `schema_version=1`, режим `parquet` или `metrics`, путь `data_dir`, SHA-256 трёх исходных Parquet в `source_sha256` и пяти CSV в `output_sha256`. В режиме `metrics` исходные Parquet не привязаны (`data_dir=null`, `source_sha256={}`). Контекст публикуется последним. UI подключает историю переводов и запасной источник метаданных Parquet к аналитике только после проверки режима, пути и всех контрольных сумм; совпадения одних GID недостаточно. Если исходный путь изменился, повторите полный расчёт из новой папки.

### `output/nodes_roles.csv`

```text
gid,role,role_score,cluster_id,priority_score,evidence
```

Одна строка на `gid` с результатом аналитики.

### `output/clusters.csv`

```text
cluster_id,n_nodes,n_seed,sum_kzt_internal,top_gids,hypothesis
```

`sum_kzt_internal` — сумма направленных весов рёбер, у которых оба конца попали в один кластер. `top_gids` содержит до пяти GID с наибольшим `priority_score`, разделённых `;`. При равенстве score используется строковый порядок GID. Гипотеза кластера описывает преобладающую роль и число seed, а не устанавливает принадлежность к преступной группе.

### `output/top_nodes.csv`

```text
rank,gid,role,priority_score,why
```

Отчёт содержит от 20 до 100 узлов, отсортированных по `priority_score` по убыванию; при равенстве — по строковому GID. Если во входе меньше 20 узлов, pipeline завершится с понятной ошибкой. CSV записываются в UTF-8 с BOM, чтобы русские объяснения открывались в табличных редакторах.

## Тесты

```powershell
python -m pip install -r requirements-test.txt
python -m unittest discover -s tests -v
```

Зависимости общего pipeline и тестов перечислены в `requirements-test.txt`. Проверяются все шесть ролей, диапазоны score, evidence, граница `depth=4`, Louvain-проекция, фиксированные колонки экспорта и минимальный размер TOP-отчёта, а также валидация данных, метрики и интерфейс. Только аналитические проверки: `python -m unittest discover -s tests -p test_analytics.py -v`.
