# TraceFlow: демонстрация UI и передача команде

Ветка: `dev/ui`. Интерфейс читает роли, приоритет и объяснения из CSV; не вычисляет
и не нормализует аналитические оценки. Ветки команды остаются раздельными;
интерфейс подключает их готовые результаты по [контракту CSV](integration.md).

## Запуск и проверка

```powershell
.\.venv\Scripts\python.exe -m streamlit run ui/app.py
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

UI-проверки включают подключение `node_metrics.csv` без исходных parquet,
совместимые названия колонок связей и сохранение трёх знаков приоритета.
Полный прогон после очистки: **47 тестов прошли**, из них **32 UI**.
Проверены загрузка, каждый mock GID, реальный GID, неизвестный GID, изолированный
клиент, seed/depth=4, переключение источников и точность длинных идентификаторов.
В живом браузере проверены переход из Top Nodes, фильтр входящих, переход к
контрагенту и возврат. На ширине 390 px проверены открытие меню поиска и поиск
реального изолированного GID. Снимки ниже сделаны при ширине 1440 px.

На чистой машине создайте `.venv`, установите `requirements-ui.txt`. Для полного
прогона тестов установите `requirements-test.txt`, включающий NetworkX и SciPy.
Готовую `.venv` не переносить между компьютерами.

## Источники и контракт

В режиме **Авто: output → mock** готовые файлы читаются из `output/`.
Если ни одного аналитического CSV ещё нет, открывается явно маркированный mock.
Частичный или некорректный `output/` не заменяется демо молча.
Режим **Демо: mock CSV** можно включить явно независимо от состояния аналитики.
Режим **Исходные данные** показывает клиентов и переводы без присвоения ролей.

| Файл | Обязательные поля |
| --- | --- |
| nodes_roles.csv | gid, role, role_score, cluster_id, priority_score, evidence |
| clusters.csv | cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis |
| top_nodes.csv | rank, gid, role, priority_score, why |
| node_metrics.csv | gid, depth, is_seed, truncated_by_depth — готовые метаданные сбора |
| edges.csv или edges.parquet | src, dst; sum_kzt и n_tx используются при наличии; для CSV также source, target, amount |

Связи для реального кейса: сначала `output/edges.*`, затем исходный `edges.parquet`.
Mock всегда использует только `mock/edges.csv`. Демо содержит 21 клиента, 20 строк
Top Nodes и 21 направленную связь, включая отдельный изолированный узел.
Скоры mock зафиксированы как тестовые данные, а не рассчитаны моделью.

Все GID в таблицах, полях выбора и SVG представлены строками, в том числе после
чтения parquet. Столбцы `gid`, `src`, `dst` не передаются как JavaScript Number.
Проверка включает соседние int64 `9007199254740992` и `9007199254740993`.

Карточка показывает evidence как обоснование роли, а why из Top Nodes — как
причину приоритета. Для клиента вне Top Nodes поддержаны необязательные поля
`priority_reason` или `priority_evidence` в nodes_roles.csv. При их отсутствии UI
прямо сообщает, что отдельное объяснение приоритета не передано.

## Один GID за 60 секунд

| Время | Действие |
| --- | --- |
| 0–10 с | Ввести GID в поиск слева или выбрать его в Top Nodes → «Открыть GID». |
| 10–25 с | На Dashboard назвать роль как гипотезу, кластер и прочитать причину приоритета. |
| 25–40 с | Включить «Входящие», затем «Исходящие». Голубая стрелка — вход, оранжевая — выход; стрелка указывает получателя. |
| 40–50 с | Выбрать «Связанный GID» → «Продолжить по связи». Вернуться кнопкой «← Предыдущий GID». |
| 50–60 с | Нажать «Скачать сводку по GID». Назвать ограничения выбранного клиента. |

Для быстрого просмотра приоритетов есть вкладка **Top Nodes** и выбор TOP-20 слева.
Граф показывает до 10 соседей на странице; остальные доступны через «Группа связей».
Счётчик показывает число видимых связей, число в фильтре и общее число связей клиента.
Сводка включает все связи клиента независимо от фильтра и страницы графа.
В Top Nodes переход доступен ко всем строкам очереди, включая позиции за пределами TOP-20.
Порядок rank и значения приоритета сохраняются как переданы аналитикой.

### Реплика для защиты

«TraceFlow помогает проверить гипотезу о клиенте по наблюдаемым переводам.
Ввожу GID: здесь роль и её основание, отдельно — причина включения в очередь.
На графе видно направление денег; я могу перейти к контрагенту и вернуться.
Для seed вход неполон, а на четвёртом колене дальнейший путь неизвестен.
Сохраняю сводку со всеми связями и оговорками для дальнейшей проверки».

### Перед выходом к жюри

1. Открыть приложение и нажать «Обновить данные». Проверить источник и количество клиентов.
2. Если виден блок «Качество выгрузки», раскрыть его и передать замечания владельцу аналитики.
3. Проверить три реальных GID ниже, неизвестный GID и переключение страниц связей.
4. Проверить Top Nodes → Dashboard → контрагент → возврат и скачивание сводки.
5. Оставить Dashboard на первом реальном GID. Если показывается mock, прямо назвать его синтетическим.

## Замечания для финальной интеграции

В актуальной `analytics@1aefc49` исправлены прежние замечания к шкале приоритета,
лимиту evidence и правилу транзита. На результатах вместе с `dev/data-metrics@8374a80`
проверены приоритеты 0–1 и evidence до 189 символов. UI показывает эти значения без пересчёта.

Передавайте пять файлов одного запуска: `node_metrics.csv`, `edges.csv` и три
аналитических CSV. Без метрик и `nodes.parquet` UI не может восстановить seed/depth;
без `transactions.parquet` недоступна дневная история отдельных переводов.

Ветки не сливались. В рабочем `src/` UI-ветки сохранена историческая реализация;
для актуальных расчётов используйте команды владельцев в их ветках. UI не вызывает
эти расчёты и не переписывает переданные файлы. Интеграционные тесты также используют
временные папки, поэтому не заменяют текущие результаты демо.
